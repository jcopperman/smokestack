# SmokeStack — Concepts

A guide to how SmokeStack works under the hood: the data flow, the components, and the design decisions.

---

## The core idea

SmokeStack separates **triggering** a test run from **executing** it. When you click "Run Suite" or call the API, the request returns immediately with a `queued` status. The actual test execution happens asynchronously in a background worker. You poll (or watch the dashboard) until the status transitions to `passed`, `failed`, or `error`.

This decoupling means the API is never blocked by slow test runs, and multiple runs can execute concurrently.

---

## Data flow: what happens when you trigger a run

```
POST /api/runs
      │
      ▼
1. API validates suite name against the registry
2. INSERT INTO runs (status = 'queued')  →  PostgreSQL
3. runQueue.add(jobId, { runId, suite, environment })  →  Redis (BullMQ)
4. API returns 201 with the run record
      │
      ▼  (async — BullMQ dequeues the job)
5. Runner picks up the job
6. UPDATE runs SET status = 'running'
7. mkdir /artifacts/<runId>/
8. Spawn subprocess: playwright / newman / k6
9. Stream stdout + stderr → /artifacts/<runId>/run.log
10. Parse results from output files
11. UPDATE runs SET status, total_tests, passed_tests, failed_tests, duration_ms, log_output
```

## Components

### API service (`api/`)

An Express app with two responsibilities:

**REST API** — handles all `/api/*` routes:
- `POST /api/runs` — validates the request, inserts a row, enqueues a job, returns immediately
- `GET /api/runs` — paginated list with optional `?status=` filter
- `GET /api/runs/:id` — single run with full results
- `GET /api/runs/:id/logs` — raw log output stored in the DB
- `GET /api/suites` — lists registered suites (drives the dashboard dropdown)

**Static file server** — serves two things from the same Express process:
- `/artifacts/:runId/...` — HTML reports, JSON results, raw logs written by the runner
- `/*` — the dashboard SPA (`public/index.html`)

### Runner worker (`runner/`)

A BullMQ worker that dequeues jobs from Redis and runs tests. It:
1. Marks the run as `running` in PostgreSQL
2. Creates a per-run artifact directory at `/artifacts/<runId>/`
3. Spawns the test tool as a child process (`spawn`, not `exec`) — this streams output in real time and avoids buffer limits
4. Waits for the process to exit, then parses results from the output files
5. Writes the final status, counts, and log tail back to PostgreSQL

The runner runs inside the **Playwright Docker image** (`mcr.microsoft.com/playwright:v1.42.0-jammy`), which means Playwright, Chromium, and Firefox are pre-installed. Newman and k6 are installed on top.

### Queue (Redis + BullMQ)

Redis is used exclusively as a job queue via BullMQ. No application state lives in Redis — all persistent data goes to PostgreSQL. Jobs are configured with:
- 2 retry attempts with a 5-second fixed backoff
- Up to 100 completed/failed jobs retained (older ones auto-removed)

The job payload is minimal — just `{ runId, suite, environment }`. The runner looks up everything else it needs from the suite registry and the filesystem.

### Database (PostgreSQL)

A single `runs` table holds all run metadata. UUIDs are generated by PostgreSQL via `pgcrypto`'s `gen_random_uuid()`. The `log_output` column stores the last 100 KB of the run's log so it's queryable without touching the filesystem. Full artifacts (HTML reports, JSON) live on disk.

Schema: [`postgres/init.sql`](postgres/init.sql)

### Artifact volume

A named Docker volume (`artifacts`) is mounted into both the API container and the runner container at `/artifacts`. The runner writes files; the API serves them. They share the same filesystem path.

## Suite registry — two halves

Each suite is registered in two separate files, each serving a different purpose:

| File | Purpose |
|---|---|
| `api/src/suites.ts` | What the API and dashboard know: name, description, type, estimated duration. Drives the `/api/suites` endpoint and the dropdown. |
| `runner/src/suites.ts` | What the runner needs to execute: tool type, working directory inside the container. |

The `id` key must match in both files — that's how the runner looks up execution config when it receives a job.

## How each test tool is executed

### Playwright

```
playwright test
```
Run from the suite's `cwd` with `ARTIFACT_DIR` injected as an env var. The suite's `playwright.config.ts` reads that env var to set the output paths for the JSON reporter and HTML reporter. The runner then parses `results.json` to extract pass/fail counts.

### Newman (Postman collections)

```
newman run collection.json \
  --reporters cli,json,htmlextra \
  --reporter-json-export results.json \
  --reporter-htmlextra-export report.html
```
If an `environment.json` exists in the suite directory, it is passed via `--environment`. The runner parses `results.json` for counts.

### k6

```
k6 run -e ARTIFACT_DIR=<path> script.js
```
k6 doesn't natively run TypeScript, so scripts stay as `.js`. The `ARTIFACT_DIR` env var is passed via `-e` so the script's `handleSummary` function can write `summary.json` to the right place. The runner parses `checks.values.passes` and `checks.values.fails` from that file.

> **Note:** `--summary-export` was removed in k6 v0.46. `handleSummary` is the replacement and must be implemented in each k6 script.

## Status lifecycle

```
queued  →  running  →  passed
                    →  failed   (exit code ≠ 0 or failed_tests > 0)
                    →  error    (execution threw — tool not found, crash, etc.)
```

`failed` means the tests ran but some assertions did not pass. `error` means the run itself could not complete (e.g. the test tool crashed or wasn't found).

---

## Result parsing

Each tool produces different output formats. The runner normalises them all into the same shape:

```typescript
interface TestResults {
  total:  number;  // total assertions / checks executed
  passed: number;  // assertions that passed
  failed: number;  // assertions that failed
}
```

| Tool | Source file | What counts as a "test" |
|---|---|---|
| Playwright | `results.json` (`stats.expected` + `stats.unexpected`) | Each `expect()` assertion |
| Newman | `results.json` (`run.stats.tests`) | Each Postman test script assertion |
| k6 | `summary.json` (`metrics.checks.values`) | Each `check()` call |

## Artifact paths

Everything the runner writes goes under `/artifacts/<runId>/`:

| File | Written by | Served at |
|---|---|---|
| `run.log` | Runner (streams process output) | `/artifacts/:id/run.log` |
| `results.json` | Playwright / Newman reporter | `/artifacts/:id/results.json` |
| `html-report/index.html` | Playwright HTML reporter | `/artifacts/:id/html-report/index.html` |
| `report.html` | Newman htmlextra reporter | `/artifacts/:id/report.html` |
| `summary.json` | k6 `handleSummary` | `/artifacts/:id/summary.json` |

The API serves these files directly from disk via `res.sendFile`. Path traversal is blocked by normalising the path and confirming it stays within `ARTIFACT_DIR`.

## Adding a suite

1. Create test files under `examples/your-suite/`
2. Add an entry to `api/src/suites.ts` (dashboard metadata)
3. Add an entry to `runner/src/suites.ts` (execution config)
4. No rebuild needed — `examples/` is bind-mounted as a live volume

See the README for tool-specific setup requirements (Playwright config, Newman collection format, k6 `handleSummary`).
